# 桌面技術堆疊與原生輸入研究

> 範圍：Windows x64、macOS Apple Silicon、Linux x64 的桌面外殼、Native Messaging host 發行，以及 OS 級快捷鍵注入。來源限 Tauri、Electron、Chrome、Mozilla、Microsoft、Apple、X.Org、Wayland/freedesktop 的第一方文件。本文把「API 有此操作」與「瀏覽器／網頁會信任或確實收到」分開；後者只能在來源明示時主張。

## 結論與建議

**建議首選 Tauri 2，將 OS input adapter 放在 Rust core 或隨附的 per-target sidecar，並把 browser host 註冊寫成每個 browser／OS 的 installer 步驟。** 這項建議只基於其已文件化的三平台 installer、platform-specific config、resource／sidecar bundling、以及 Apple-Silicon `aarch64-apple-darwin` sidecar target 命名；並**不**表示 Tauri 會自動安裝 extension、產生 browser host manifest，或繞過任何 OS input permission。 [Tauri Distribute](https://v2.tauri.app/distribute/)；[Tauri Configuration Files](https://v2.tauri.app/develop/configuration-files/)；[Tauri Sidecars](https://v2.tauri.app/develop/sidecar/)

Electron 也是可行替代：其官方 release matrix 列 macOS Apple Silicon/ARM、Windows x64、Linux x64 binary，並推薦 Electron Forge 產生 OS-specific distributables；`app.getPath('userData')` 是配置檔的慣例位置。可是 Electron core 不包含 packaging/distribution tooling，且其文件同樣沒有「安裝 Native Messaging host」功能。因此它不降低瀏覽器登錄或 input adapter 的工作量。 [Electron platform support](https://raw.githubusercontent.com/electron/electron/v44.1.1/README.md)；[Electron packaging](https://electronjs.org/docs/latest/tutorial/tutorial-packaging)；[Electron userData](https://electronjs.org/docs/latest/api/app)

任何方案都只能承諾**前景依序 best-effort**：實體鍵盤一次只會有一個 OS focus target，無來源提供跨兩個 browser/tab 的 focus+inject transaction。不得宣稱 synthetic chord 是 browser/page `trusted`、兩個 tab 同時收到、exactly-once，或在所有 Linux desktop session 可用。

## Native Messaging host 與 extension 安裝

桌面外殼只負責把 host binary／manifest 放進安裝物；**browser 才定義 host discovery 與 extension policy**。host manifest 也必須 allowlist 精確 extension identity，不能把任意 extension 接到本機 process。

| Browser surface | Windows x64 | macOS Apple Silicon | Linux x64 | 安裝流程與限制 |
| --- | --- | --- | --- | --- |
| Chrome / Chromium | installer 寫 `HKCU` 或 `HKLM\\SOFTWARE\\Google\\Chrome\\NativeMessagingHosts\\<name>`，default value 是 manifest 的完整路徑。 | system/user `NativeMessagingHosts` 固定 locations；host `path` 必須 absolute。 | system/user `NativeMessagingHosts` 固定 locations；host `path` 必須 absolute。 | host manifest 必須有 `allowed_origins` 精確列 `chrome-extension://<id>/`，extension 需 `nativeMessaging` permission。Chrome external extension install 在 Windows/macOS 仍會要求使用者確認啟用；Linux external install 可自動安裝，並有不同 source rules。 [Chrome Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)；[Chrome runtime](https://developer.chrome.com/docs/extensions/reference/api/runtime)；[Chrome alternative install methods](https://developer.chrome.com/docs/extensions/how-to/distribute/install-extensions) |
| Firefox | `HKCU`/`HKLM\\Software\\Mozilla\\NativeMessagingHosts\\<name>` 指向 manifest。 | fixed system/user manifest locations。 | fixed `/usr/lib`、`/usr/lib64` 或 user manifest locations。 | Firefox 明定 host 是由 underlying OS installation machinery 安裝，browser 不安裝或管理它；manifest 以 `allowed_extensions` allowlist Add-on ID。故 Firefox extension 與 host manifest 是 browser-specific package/config。 [Mozilla Native Messaging](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Native_messaging)；[Mozilla Native manifests](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Native_manifests) |
| Brave | **未找到 Brave 第一方 host registry/location 文件。** | **未找到。** | **未找到。** | Brave 第一方只說可使用 Chrome Web Store extensions、MV3 extensions 如 Chrome 運作；這不是 Native Messaging discovery 的逐平台保證。installer 不得套用 Google Chrome key/path 後就宣稱 Brave 已支援；需先取得 Brave 官方確認或三平台實機 evidence。 [Brave extension support](https://brave.com/learn/using-chrome-extensions-in-brave/) |

因此 installer 的必要工作是：(1) 放置正確 architecture host executable，(2) 產生每 browser 的 allowlisted manifest，(3) 寫 Chrome/Firefox 規定的 registry key 或 fixed-location file，(4) 清楚引導使用者完成 browser extension 的 permission/enable UI，(5) uninstall 時只移除本產品的登錄與檔案。這是受文件支持的 packaging plan；Brave 第 (3) 項仍是 blocker，不可猜測。

## OS input adapter 比較

| 平台 | 文件化注入 surface 與可用 desktop | permission / session gate | trusted？ | chord 內原子性／delivery 結論 |
| --- | --- | --- | --- | --- |
| Windows x64 | `SendInput` 將 `INPUT` array 插入 keyboard/mouse input stream。interactive window station 同時只有一個可見、接收 user input 的 input desktop；`OpenInputDesktop` 取得該 desktop。 | `SendInput` 受 UIPI 約束，只能 inject 至同或較低 integrity level；UAC/Winlogon 是不同 secure desktop，且只有一個 active input desktop。非 interactive/service process 不可假設能對使用者 desktop 輸入。 | **無保證。** `SendInput` 文件稱 synthesize/insert events，未把其定義成 browser 或 DOM trusted event。 | **同一次 `SendInput` array 有文件化的串列原子性：其中 events 不會與 user、`keybd_event`、`mouse_event` 或其他 `SendInput` 插入 events 交錯。** 仍沒有 target focus、browser handling、兩次 target switch，或跨 browser 的 transaction 保證；將 modifier-down/key-down/key-up/modifier-up 放在同一 array 只能縮小 OS-stream interleaving。 [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)；[Windows desktops](https://learn.microsoft.com/en-us/windows/win32/winstation/desktops)；[OpenInputDesktop](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-openinputdesktop) |
| macOS Apple Silicon | 建立 `CGEvent(keyboardEventSource:virtualKey:keyDown:)`，再以 `post(tap:)` 將單一 Quartz event 放入指定 event stream location。 | Apple 說第三方 app 試圖透過 Accessibility features 存取／控制 Mac 時，使用者必須在 Privacy & Security 明確授權；`AXIsProcessTrusted`/`AXIsProcessTrustedWithOptions` 可查詢 trusted accessibility client。Secure Event Input 可使系統停止把 keyboard events 交給 interception process。 | **無保證。** Quartz API 文件只稱建立／post Quartz event；「trusted accessibility client」是 OS 對控制 app 的 TCC trust status，不是瀏覽器或網頁將 synthetic keyboard event 視為 trusted 的契約。 | **無批次原子保證。** keyboard-event constructor 和 `post(tap:)` 都是單一 event surface；來源沒有說連續多個 post 不會與 user input／focus change 交錯，也沒有跨 application/two-tab delivery transaction。應逐一 post 並將結果定義為 best-effort。 [CGEvent keyboard constructor](https://developer.apple.com/documentation/coregraphics/cgevent/init(keyboardeventsource:virtualkey:keydown:))；[CGEvent](https://developer.apple.com/documentation/coregraphics/cgevent)；[AXUIElement APIs](https://developer.apple.com/documentation/applicationservices/1462095-axuielementcreatesystemwide)；[Apple Accessibility permission](https://support.apple.com/guide/mac-help/allow-accessibility-apps-to-access-your-mac-mh43185/mac)；[Secure Event Input](https://developer.apple.com/library/archive/technotes/tn2150/_index.html) |
| Linux x64 — X11 | X.Org XTEST `XTestFakeKeyEvent` 要求 X server simulate `KeyPress` 或 `KeyRelease`；XTEST protocol 說 synthetic device action 可觸發 event propagation/passive grabs，如同相應 input-device action。 | 僅在連得上且 server 支援 XTEST 的 **X11** session；API 本身不是 Wayland client API。 | **無瀏覽器／DOM trust 保證。** XTEST 的「如 input device action」只定義 X server 的 event processing，沒有保證 browser/page `isTrusted`、user activation 或保留快捷鍵結果。 | 每個 key press/release 都是一個 fake-event request；XTEST protocol 目前的 event list 只能長度一。因此文件沒有一個 chord batch 的 no-interleaving promise；server 按收到的 request 順序處理，但不能把多 request 當原子 chord 或 two-tab transaction。 [XTEST protocol](https://x.org/docs/Xext/xtest.pdf)；[XTEST library](https://x.org/releases/X11R7.6/doc/libXtst/xtestlib.html) |
| Linux x64 — Wayland | Wayland client 是 compositor 的 input **receiver**：kernel input 由 compositor 選擇目標 window 後才送 client。一般 client protocol 沒有 global keyboard injection request。受支援的較高權限選項是 XDG Remote Desktop portal：建 session → `SelectDevices(KEYBOARD)` → `Start()`，Start 會顯示 user dialog；取得 KEYBOARD grant 後才可 `NotifyKeyboardKeycode`，或以推薦的 EIS sender 送 input。 | portal 以 user-controlled permission system 保護資源，且 Remote Desktop portal backend／功能必須實際存在並 grant；這不是普通 Wayland client 可無提示使用的能力。 | **無保證。** Portal 文件只定義已授權 session 的 input transport，不定義 browser/page trusted event。 | **無批次原子保證。** `NotifyKeyboardKeycode` 是單 keycode/state method；EIS 亦只被文件化為 input event transport。未見「一個 chord」或跨 focus 的 atomic guarantee，且 portal 在 EIS 連線後禁止混用 Notify methods。 [Wayland Architecture](https://wayland.freedesktop.org/docs/book/Architecture.html)；[XDG portals for app developers](https://flatpak.github.io/xdg-desktop-portal/docs/for-app-developers.html)；[Remote Desktop portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html) |

### adapter 規格後果

1. 啟動時必須辨識 OS 與 interactive GUI session。Windows 僅在可用 input desktop 且 target integrity 合法時提供 `SendInput`；macOS 先檢查／請求 Accessibility grant，secure-input 期間 fail closed；Linux 依 session 分流，X11 需探測 XTEST，Wayland 需檢查 Remote Desktop portal backend、使用者 grant 與 active session。沒有 adapter 就顯示 unsupported，不能降級成 DOM event。
2. 向兩個 tab 派送時，extension 先驗證並 focus 第一個 browser window，host 注入一個 chord；再重新驗證、focus 第二個 window、注入。每一步都可被 user、OS、browser policy 或 target lifecycle 改變。任何失敗停止後續工作並回報未保證 delivery。
3. Windows 可將完整 chord 放入同一 `SendInput` 呼叫，這是唯一在所查官方 surface 中有明確 no-interspersing 語句者；它仍不是 tab-level atomicity。macOS、X11、Wayland 一律標示為逐 event best-effort。
4. 不把任何 OS injection 的成功回傳轉譯成 `trusted`／`delivered`。僅能報告「OS API accepted/posted」；是否被 browser shortcut、web content、secure field 或 OS 保留組合處理，不在上述 API 契約內。

## 未決事項與發布前 evidence

* **Brave Native Messaging lookup**：缺第一方 registry/location 文檔；必須在不猜測 Chrome path 的前提下取得 Brave 官方答覆或測試 evidence。
* **macOS distribution channel**：來源支持 Accessibility consent 與簽署/notarization，但未證明此類 CGEvent-control app 可通過 Mac App Store sandbox/review；選 App Store 前需另做 Apple policy research。
* **Linux coverage**：X11 與 Wayland 是不同 adapter contract；Wayland portal availability/approval 由 compositor/portal backend 決定。不能承諾所有 distro/desktop 或 headless/remote session。
* **browser/page trust 與 end-to-end delivery**：本研究沒有任何 OS API source 將 injected event 定義為 Chromium/Firefox/Brave 或 DOM trusted input；也沒有 source 定義雙 browser/tab 的 atomic dispatch。此二項必須保留為不保證，而非用實作推論補足。
